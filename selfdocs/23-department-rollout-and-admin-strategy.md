# 23. Department Rollout and Admin Strategy

## 대상 독자

운영 관리자/플랫폼 담당 (입문자는 `22-tenant-vs-account-explained.md`, `24-auth-api-keys-rbac-operations.md` 선행 권장)

## 목적

GoClaw를 부서원에게 안전하게 배포하면서, 관리자 대시보드는 보호하고, 부서 단위 협업(Agent Team/Agent 협업)을 운영 가능한 형태로 정리합니다.

## 전제 문제

요구사항:

- 부서원은 GoClaw 기능을 쓰게 하고 싶다
- 관리자 대시보드(전체 권한)는 열어주고 싶지 않다
- 부서 단위 업무에서 agent 협업까지 활용하고 싶다

핵심 전략:

- "운영 관리자 영역"과 "부서 사용자 영역"을 분리
- 사용자에게는 제한된 인터페이스(API 또는 사내 프론트)만 제공
- 에이전트 협업은 정책적으로 설계(자동/명시/수동)해서 사용

## 권장 제공 모델 (가장 현실적)

### 모델 A: 사내 포털 + GoClaw API 백엔드 연동 (권장)

1. 부서원은 사내 포털만 사용
2. 포털 백엔드가 GoClaw HTTP/WS 호출
3. 부서원에게 GoClaw 관리자 대시보드 URL/토큰 미공개

장점:

- 권한 통제 쉬움
- UI/업무 프로세스 커스터마이징 쉬움
- 감사 로그/승인 흐름 붙이기 용이

### 모델 B: GoClaw 대시보드 직접 사용 + 강한 권한 제한

1. 대시보드는 열되, 사용자 역할을 viewer/operator로 제한
2. admin/owner 권한은 운영팀만 유지

주의:

- 기능 노출 통제가 상대적으로 어려움
- 잘못 구성하면 운영 기능이 노출될 수 있음

## 관리자 대시보드는 어떻게 막나

실무적으로는 다음을 함께 적용:

1. 네트워크 레벨 제한
   - 관리자 대시보드 접근 IP/VPN 제한
2. 계정/권한 분리
   - 운영자(owner/admin) 계정은 소수만
   - 부서원은 tenant-bound key + 제한 role
3. 토큰 분리
   - gateway token/system key는 운영 백엔드에서만 사용
   - 사용자 브라우저/클라이언트에 노출 금지
4. API 경유 제공
   - 부서원 트래픽은 사내 백엔드 경유

## 관리자 운영 전략 (운영팀 관점)

### 1) Tenant/Role 운영

- 부서별 tenant 분리(또는 팀/프로젝트 분리)
- 기본 역할:
  - owner/admin: 플랫폼 운영팀
  - operator: 부서 리더/파워유저
  - viewer: 일반 사용자(필요 시)

### 2) Agent 카탈로그 운영

- 공용 Agent 템플릿을 먼저 정의
  - 예: "기획도우미", "개발도우미", "리뷰어", "리포트봇"
- 부서별 허용 Tool/Provider를 화이트리스트로 관리

### 3) 품질/비용 운영

- traces/usage로 부서별 사용량 및 품질 모니터링
- 고비용 모델은 특정 업무/역할에서만 허용

### 4) 보안 운영

- API 키 주기적 교체
- exec/browser 등 고위험 tool은 승인 정책 적용
- 감사 로그/이상 패턴 알림 체계 운영

## 부서 협업 구조 (모듈 단위 + 전체 단위)

## 모듈 단위 협업 (권장 시작점)

예: 개발부서

- 요구사항 모듈: PM Agent + Spec Agent
- 구현 모듈: Coder Agent
- 검증 모듈: Reviewer Agent + QA Agent
- 배포 모듈: Release Agent

운영 방법:

1. 모듈별 Agent Team 생성
2. `team_tasks`로 업무를 카드화
3. `delegate`/`spawn`으로 하위 작업 분배
4. 완료 조건/품질 게이트를 task 상태 전이에 반영

## 전체 단위 협업 (Cross-module)

예: 월간 릴리즈

1. 중앙 Coordination Team이 상위 task 생성
2. 모듈 팀으로 하위 task 위임
3. 모듈 팀 결과를 중앙 팀이 통합/승인

핵심:

- 모든 협업을 채팅이 아니라 task 중심으로 남겨야 운영 추적 가능

## 질문 핵심: "Agent끼리 알아서 대화/호출하나?"

정답: "부분 자동 가능, 하지만 기본은 연결/정책 설계가 필요"

### 실제 동작 모델

1. 자동 모드(auto)
   - 조건이 맞으면 에이전트가 적절한 협업 도구(`delegate`, `spawn`, `team_tasks`)를 선택해 실행 가능
2. 명시 모드(explicit)
   - 사용자가 "누구에게 무엇을 위임"할지 명확히 지시
3. 수동 모드(manual)
   - 운영자/사용자가 팀 보드에서 직접 할당/전환

즉, "아무 연결 없이 완전 자율 협업"이 기본은 아닙니다.

- 사전 조건:
  - 팀/링크/권한/도구 허용 정책 구성
  - 어떤 agent가 누구와 협업 가능한지 관계 정의
  - task/승인 규칙 정의

## 실전 구성 절차 (부서 배포용)

1. tenant/role 설계
2. 부서용 agent 카탈로그 확정
3. 팀 구조 생성 (모듈 단위)
4. 협업 정책 선택(auto/explicit/manual)
5. 도구 정책/승인 흐름 설정
6. 파일럿 부서 1개로 2주 검증
7. 성공 패턴 템플릿화 후 전사 확장

## 운영 시나리오 예시

시나리오: "부서원이 신규 기능 개발 요청"

1. 사용자 -> 포털에 요청 입력
2. Coordination Agent가 요구를 파싱하고 task 생성
3. Coder Agent에 구현 위임
4. Reviewer Agent에 자동 리뷰 위임
5. 결과를 사용자에게 통합 보고

이 흐름에서 관리자 대시보드는 열지 않아도 됨(포털 백엔드가 GoClaw와 통신).

## 체크리스트

- 부서원에게 관리자 토큰/대시보드 URL이 노출되지 않는다
- tenant/role/API key 경계가 문서화되어 있다
- 팀 협업 규칙(위임 조건, 승인 조건, 완료 조건)이 명확하다
- auto 협업을 켜기 전, explicit/manual로 먼저 검증했다
